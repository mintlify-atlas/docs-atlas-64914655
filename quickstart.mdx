This guide walks you through setting up CNEL Analytics on a local machine from scratch. By the end you will have a fully functional instance of the application running at `http://localhost:8000`, connected to both the CNEL EP SQL Server cloud database and a local PostgreSQL database for user management.

## Prerequisites

<Note>
  Before starting, make sure the following are available on your machine:

  - **Python 3.10 or later** — required for all backend dependencies
  - **ODBC Driver 17 for SQL Server** — required by pyodbc to connect to the CNEL EP cloud database ([Microsoft install guide](https://learn.microsoft.com/en-us/sql/connect/odbc/download-odbc-driver-for-sql-server))
  - **Access credentials for the CNEL EP SQL Server instance** — server address, database name, username, and password provided by your DBA
  - **A running PostgreSQL instance** — local or remote, used to store users, roles, and access logs
</Note>

<Steps>
  <Step title="Clone the repository">
    Clone the project from GitHub and navigate into the project root directory.

    ```bash
    git clone https://github.com/HectorRomero18/CNEL-ANALITYCS.git
    cd CNEL-ANALITYCS
    ```
  </Step>

  <Step title="Install dependencies">
    Install all Python dependencies from the pinned `requirements.txt`. Using a virtual environment is strongly recommended.

    ```bash
    python -m venv .venv
    source .venv/bin/activate      # macOS / Linux
    # .venv\Scripts\activate       # Windows
    pip install -r requirements.txt
    ```

    This installs FastAPI, SQLAlchemy, Jinja2, PyJWT, psycopg2, pyodbc, pandas, openpyxl, uvicorn, and all their pinned transitive dependencies.
  </Step>

  <Step title="Configure the environment">
    Create a `.env` file in the project root. This file must never be committed to version control — it is already listed in `.gitignore`.

    ```bash
    # Generate a secure SECRET_KEY first:
    python -c "import secrets; print(secrets.token_urlsafe(48))"
    ```

    Then create the `.env` file with the following variables, replacing every placeholder with your actual values:

    ```ini
    # ── Security ──────────────────────────────────────────────────────────
    SECRET_KEY=your-generated-secret-key-here

    # ── CNEL EP Cloud Database (SQL Server, read-only) ────────────────────
    CLOUD_DB_SERVER=your.sqlserver.host
    CLOUD_DB_NAME=CNEL_DB
    CLOUD_DB_USER=your_db_user
    CLOUD_DB_PASSWORD=your_db_password
    CLOUD_DB_DRIVER=ODBC Driver 17 for SQL Server

    # ── Local Database (PostgreSQL, read-write) ───────────────────────────
    LOCAL_DB_HOST=localhost
    LOCAL_DB_PORT=5432
    LOCAL_DB_NAME=cnel_local
    LOCAL_DB_USER=postgres
    LOCAL_DB_PASSWORD=your_pg_password
    ```

    `SECRET_KEY` signs and validates every JWT token. `CLOUD_DB_DRIVER` must match the exact driver name returned by your ODBC installation — verify it with `odbcinst -q -d` on Linux or the ODBC Data Sources manager on Windows.
  </Step>

  <Step title="Start the development server">
    From the project root, launch the application with uvicorn. The `--reload` flag enables automatic restarts on code changes.

    ```bash
    uvicorn backend.main:app --reload
    ```

    Once started you will see output similar to:

    ```
    INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
    INFO:     Started reloader process using WatchFiles
    INFO:     Started server process
    INFO:     Waiting for application startup.
    INFO:     Application startup complete.
    ```

    The application is now available at **http://localhost:8000**. The Jinja2 frontend views, JSON API routes (`/api/clientes/*`, `/api/export/*`, `/auth/*`, `/admin/*`), and static assets are all served from this single process.
  </Step>

  <Step title="Log in">
    Open **http://localhost:8000** in your browser. If no active session is detected you will be shown the login page. Enter a valid staff username and password.

    On successful authentication the server calls `POST /auth/login`, verifies the bcrypt password hash against the PostgreSQL `usuarios` table, and issues a signed JWT token. That token is written directly into an HttpOnly cookie named `access_token` — you do not need to copy or store it manually. All subsequent requests to protected routes automatically include the cookie, and the `login_required` decorator on each view validates it transparently before rendering any page.
  </Step>
</Steps>

<Warning>
  `SECRET_KEY` must be at least 32 characters long — the application will raise a `RuntimeError` at startup and refuse to start if this requirement is not met. Changing `SECRET_KEY` after deployment immediately invalidates all existing JWT tokens, forcing every user to log in again.
</Warning>
